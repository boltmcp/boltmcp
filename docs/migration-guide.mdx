---
title: Migration Guide
description: Breaking changes to apply before upgrading BoltMCP, listed by chart version.
---

Read this page before every [upgrade](./upgrading), and work through each section between the version you have installed and the version you are moving to. Everything here must be done **before** `helm upgrade` runs: a pod whose Deployment references a Secret key that does not exist yet never starts, and a values file carrying a removed key fails schema validation before Helm applies anything.

To check which version you are on:

```bash
helm list -n boltmcp
```

## Set Variables

Export the Helm release name and namespace so the commands below can be pasted verbatim. Both default to `boltmcp` — adjust if you installed under different names.

```bash
export RELEASE=boltmcp
export NAMESPACE=boltmcp
```

## 0.5.x

Before upgrading, rename the client secret for BoltMCP's Management REST API:

```bash
kubectl patch secret ${RELEASE}-oidc -n ${NAMESPACE} --type json -p '[
  {"op": "move",
   "from": "/data/rest-api-resource-server-client-secret",
   "path": "/data/rest-api-to-keycloak-client-secret"}
]'
```

Confirm the new key is present and non-empty before upgrading:

```bash
kubectl get secret ${RELEASE}-oidc -n ${NAMESPACE} \
  -o go-template='{{range $k, $v := .data}}{{$k}}={{len $v}}{{"\n"}}{{end}}'
```

The client `boltmcp-rest-api` is now redundant, and you may optionally delete it from the Keycloak Admin Console.

## 0.4.x

Two additional keys are now required in the [`boltmcp-auth`](./cluster-preparation#boltmcp-auth) Secret:

| Key | Used for |
|---|---|
| `mcp-inspector-api-token` | Bearer token the MCP Inspector's own backend API expects, and that boltmcp-web's "Open in Inspector" links carry |
| `mcp-server-upstream-oauth-secret` | Root secret for the MCP server's upstream-OAuth crypto keys (≥ 32 chars) |

<Callout type="warn">
    `mcp-inspector-api-token` is not a network access control. The Inspector serves its own token to any browser that can load its page, so the token is only as private as the Inspector's hostname.
</Callout>

Generate both values into shell variables first, then patch. A merge patch against `stringData` leaves the keys already in the Secret untouched:

```bash
INSPECTOR_TOKEN=$(openssl rand -hex 32)
UPSTREAM_OAUTH_SECRET=$(openssl rand -hex 32)

kubectl patch secret ${RELEASE}-auth -n ${NAMESPACE} --type merge -p "{
  \"stringData\": {
    \"mcp-inspector-api-token\": \"${INSPECTOR_TOKEN:?not generated}\",
    \"mcp-server-upstream-oauth-secret\": \"${UPSTREAM_OAUTH_SECRET:?not generated}\"
  }
}"
```

Confirm both keys are present and non-empty before upgrading:

```bash
kubectl get secret ${RELEASE}-auth -n ${NAMESPACE} \
  -o go-template='{{range $k, $v := .data}}{{$k}}={{len $v}}{{"\n"}}{{end}}'
```

<Callout>
    The number is the length of the base64-encoded value, not the character count of the secret.
</Callout>

The upgrade rolls the pods that consume these keys, so there is no separate restart to run afterwards.
